# BT-210 링크 시험 도구 — LinkTest_Leader / LinkTest_Robot

> **팀 저장소용 안내**: 이 도구는 다른 설계안(AI 생성 설계 패키지) 폴더에서 옮겨 온 것입니다. 아래 본문에 나오는 `LeaderArm_OpenRB`·`ManualRobot_OpenRB`·`조종기_OpenRB/…`·`6_코드/…`는 그 설계안의 펌웨어입니다. 팀 코드로 읽을 때는 각각 `teleoperation /Leader_Grip_Track.ino`(조종기)와 `teleoperation /Follower_Grip_Track.ino`(로봇)로 바꿔 읽으세요. 팀 코드의 끊김 기준은 0.3초가 아니라 0.5초(`ARM_LINK_TIMEOUT_MS = 500`)이고, 조종기는 25 ms마다(40 Hz) 보냅니다. 6단계(모터를 돌리면서)는 상위 폴더의 BTLOG 로그 빌드로 하는 것이 더 낫습니다(`../README.md`).

조종기(리더 팔)와 수동로봇 사이의 블루투스(BT-210 한 쌍) 링크가 **경기장 조건에서도 쓸 만한지** 대회 전에 숫자로 재는 도구입니다.
경기에 쓰는 **바로 그 두 OpenRB-150 보드와 그 BT-210 한 쌍**에 시험 스케치를 잠깐 올려서 잽니다. 시험이 끝나면 원래 펌웨어를 다시 올립니다.

| 파일 | 올리는 곳 | 내용 |
|---|---|---|
| `LinkTest_Leader/LinkTest_Leader.ino` | 조종기 보드 (BT-210 **마스터**) | 20 ms마다 시험 줄을 보내고, 돌아온 응답으로 왕복 시간·손실·끊김을 잰다 |
| `LinkTest_Robot/LinkTest_Robot.ino` | 로봇 보드 (BT-210 **슬레이브**) | 시험 줄을 받아 곧바로 응답하고, 혼자서도 '가는 길' 손실·공백·묵은 줄을 잰다 |
| `README.md` | — | 이 문서 |

**순서**: 2장(올리기) → 5장(시험 순서대로 재기, 결과는 4장 기준으로 판정) → 시험 끝나면 **원래 펌웨어 다시 올리기**(2장 끝)

> 이 도구는 컴파일(경고 0개)과 PC 모의시험까지만 거쳤고, 실제 보드에서는 아직 돌려 보지 못했습니다(9장).
> 처음 올렸을 때 1단계(가까이)에서 숫자가 말이 되는지부터 확인하세요.

## 1. 무엇을 재나

```
  조종기 보드 (LinkTest_Leader)                                  로봇 보드 (LinkTest_Robot)
  BT-210 마스터                                                  BT-210 슬레이브
     │  20 ms마다  T,000123,00045678,tuv*07\n  (25바이트) ──────▶  체크섬 확인 → 곧바로 응답
     │                                                                 │
     ◀────────  R,000123,00045678,000120*75\n  (28바이트)  ───────────┘
     │          (번호·시각은 받은 줄 그대로, 000120 = 로봇이 지금까지 제대로 받은 줄 수)
     ▼
  왕복 시간 = 지금 시각 - 그 줄을 보낸 시각
```

- 시험 줄은 실제 조종기 줄(`p1,p2,p3,p4,g*CC`, 13~32바이트, 평균 약 25바이트)과 **길이·주기·체크섬 방식이 같습니다**.
  내용만 다릅니다(번호와 시각). 그래서 실제 펌웨어와 섞어 쓸 수 없습니다(실제 로봇 펌웨어는 시험 줄을 전부 버린다).
- 응답에 '로봇이 받은 줄 수'가 실려 있어서, 조종기 화면 하나만 보고도 손실을 **가는 길(조종기 → 로봇)** 과
  **오는 길(로봇 → 조종기)** 로 나눠 볼 수 있습니다. 실제 경기에서 중요한 것은 **가는 길**입니다.

| 재는 것 | 어디에 나오나 | 뜻 | 실제 경기에서는 |
|---|---|---|---|
| 손실 | 조종기 | 1초(`REPLY_TIMEOUT_MS`) 안에 응답이 안 온 줄의 비율 (가는 길 + 오는 길) | — |
| 가는길 / 오는길 | 조종기 | 위 손실을 방향별로 나눈 값(늦게 온 응답과 로봇 재부팅 동안 잃은 줄은 빠지므로 둘을 더해도 손실보다 작을 수 있다) | 가는길 손실 = 로봇이 못 받은 팔 명령 |
| 빠진번호 | 로봇 | 로봇이 받은 줄 번호 사이에 빠진 번호의 비율 (가는 길만) | 로봇이 못 받은 팔 명령 |
| 왕복 ms 최소/중간/95%/최대 | 조종기 | 보낸 뒤 응답이 오기까지 걸린 시간의 분포. 95% = 100줄 중 95줄이 이 안에 왔다 | 한쪽 지연은 대략 왕복의 절반(추정) |
| 가장 긴 무응답 / 300 ms 넘는 끊김 | 조종기 | 제때 온 응답과 응답 사이의 가장 긴 시간 / 0.3초 넘게 끊긴 횟수 | 0.3초 넘게 끊기면 로봇 팔이 그 자리에 멈춘다 |
| 가장 긴 공백 / 300 ms 넘는 공백 | 로봇 | 제대로 된 줄과 줄 사이의 가장 긴 시간 / 0.3초 넘는 횟수 (가는 길만) | 위와 같음. **이 값이 실제 팔 멈춤과 가장 가깝다** |
| 묵은 줄 | 로봇 | 평소보다 0.3초 넘게 늦게 도착한 줄. 끊긴 동안 모듈에 쌓였다가 한꺼번에 나온 줄로 보인다 | 로봇이 **지난 자세**로 움직인다(위험) |
| 늦게 도착(가장 빠른 줄 대비) | 로봇 | 줄마다 '조종기 시각 → 로봇 시각' 차이가 그 5초 동안 가장 빨리 온 줄보다 얼마나 큰가 | 지연이 흔들리는 정도. 팔이 툭툭 끊겨 보이는 원인 |
| 늦게옴 | 조종기 | 1초가 지나 손실로 센 뒤에 도착한 응답 | 묵은 줄과 같은 현상을 조종기 쪽에서 본 것 |
| 체크섬틀림 / 형식틀림 | 둘 다 | 체크섬이 틀린 줄 / 잘린 줄·이어 붙은 줄·이상한 글자 | 로봇은 버린다(= 손실과 같다) |
| 순서뒤바뀜 / 중복 / 모르는번호 | 둘 다 | 앞선 번호가 늦게 옴 / 같은 번호가 또 옴 / 보낸 적 없는 번호 | 보통은 0이어야 한다 |
| BT건너뜀 / 응답건너뜀 | 조종기 / 로봇 | 보드의 블루투스 송신 버퍼에 자리가 없어 그 줄을 안 보냈다 | 0이어야 한다. 0이 아니면 설정 문제 |
| 첫 응답 / 첫 줄: 부팅 뒤 x초 | 조종기 / 로봇 | 보드가 켜지고 링크가 이어져 첫 줄이 오기까지 걸린 시간 | 경기 중 한쪽이 꺼졌다 켜지면 팔이 이만큼 멈춘다 |

**이 도구로 재지 못하는 것** (9장에 자세히)

- 시험 스케치는 다이나믹셀을 쓰지 않아 **모터가 돌지 않습니다**. 모터를 돌릴 때의 영향은 5장 6단계처럼 실제 펌웨어로 봅니다.
- 두 보드의 시계가 따로 놀기 때문에 '한쪽 지연'의 절대값은 못 잽니다. 왕복 시간과 '늦게 도착한 정도'(상대값)만 잽니다.
- 응답을 돌려보내므로 실제 경기(조종기 → 로봇 한 방향)보다 블루투스가 조금 더 바쁩니다.
  실제처럼 한 방향만 재려면 로봇 쪽 `ECHO_ENABLED = false` 로 올리고 로봇 쪽 숫자만 봅니다.

## 2. 올리기 (업로드)

준비는 조종기 펌웨어와 같습니다(`조종기_OpenRB/읽어보기.md` 4장: 보드 관리자에서 Arduino SAMD Boards와 OpenRB-150 보드 설치).
**다른 라이브러리는 필요 없습니다**(Dynamixel2Arduino도 안 씀). 확인한 보드 패키지: OpenRB-150 0.2.1.

1. **조종기 보드**(BT-210 마스터가 꽂힌 보드)에 `LinkTest_Leader/LinkTest_Leader.ino` 를 엽니다(폴더 이름과 파일 이름을 바꾸지 않는다).
   `도구 > 보드 > OpenRB-150`, 포트를 고르고 업로드.
2. **로봇 보드**(BT-210 슬레이브가 꽂힌 보드)에 `LinkTest_Robot/LinkTest_Robot.ino` 를 같은 방법으로 업로드.
3. 두 보드의 시리얼 모니터를 엽니다(속도는 아무 값이나). 맨 위에 `==== BT-210 링크 시험 ...` 안내문이 나오고,
   5초마다 요약 두 줄이 나오면 정상입니다. 몇 초 안에 `[알림] 첫 응답 받음` / `[알림] 첫 줄 받음` 이 나와야 합니다.

명령줄로 올릴 때(선택):

```
arduino-cli compile --fqbn OpenRB-150:samd:OpenRB-150 LinkTest_Leader
arduino-cli upload  --fqbn OpenRB-150:samd:OpenRB-150 -p COM? LinkTest_Leader
```

주의할 점

- **두 BT-210은 경기 때와 같은 보드, 같은 자리에 둡니다.** 짝(마스터/슬레이브)은 모듈 안에 저장되어 있어 스케치와 상관없습니다.
  모듈을 바꿔 끼우면 경기 때와 다른 것을 재게 됩니다.
- BT-210은 **보드 전원을 끈 상태에서** 꽂고 뺍니다(ROBOTIS 설명서의 주의 사항, 8장 출처 [1]).
- **로봇 팔에 힘이 없습니다.** 시험 스케치는 다이나믹셀 전원을 켜지 않으므로 팔이 처집니다. 올리기 전에 팔을 접어 두거나 받쳐 둡니다.
  바퀴도 돌지 않고, 무선조종 수신기도 읽지 않습니다.
- 로봇 보드는 **경기 때처럼 배터리로** 켭니다(전원 상태가 블루투스에 영향을 줄 수 있으므로). 조종기 보드는 경기 때처럼 USB로.
- 업로드가 안 되면 리셋 단추를 빠르게 두 번 누르고 다시 업로드합니다.

**시험이 끝나면 반드시 원래 펌웨어로 되돌립니다.**
조종기 보드 ← `teleoperation /Leader_Grip_Track.ino`(또는 로그 빌드 `teleoperation_log/Leader_Grip_Track_Log`), 로봇 보드 ← `teleoperation /Follower_Grip_Track.ino`(또는 `teleoperation_log/Follower_Grip_Track_Log`).
(시험 스케치가 남아 있으면 조종기는 팔 각도를 보내지 않고, 로봇은 팔·바퀴를 움직이지 않습니다)

## 3. 결과 읽는 법

### 3.1 조종기 쪽 요약 (5초마다 두 줄)

아래 숫자는 **보기 위한 예시**입니다(실제로 잰 값이 아님).

```
[5초 #12 단계2 합격] 보냄 250 응답 250 손실 0(0.00%) 가는길 0.00% 오는길 0.00% | 왕복 ms 최소 31 중간 38 95% 47 최대 55 | 가장 긴 무응답 41 ms, 300 ms 넘는 끊김 0번 | 체크섬틀림 0 형식틀림 0 순서뒤바뀜 0 중복 0 늦게옴 0 모르는번호 0 BT건너뜀 0
[누적 1분00초 단계2 합격] 보냄 3000 응답 2998 손실 2(0.07%) 가는길 0.03% 오는길 0.03% | 왕복 ms 최소 30 중간 38 95% 48 최대 92 | 가장 긴 무응답 82 ms, 300 ms 넘는 끊김 0번 | ... | 불합격 구간 0/12 | 첫 응답: 부팅 뒤 2.1초
```

- 대괄호 안: `5초 #번호` 또는 `누적 경과시간`, 단계 번호, **판정**(합격 / 주의 / 불합격)과 그 까닭.
  예: `[5초 #31 단계3 불합격: 손실 1.60%, 무응답 410 ms]`
- `보냄`은 5초에 250이어야 합니다(50 Hz). `응답 + 손실`은 `보냄`과 조금 다를 수 있습니다:
  손실은 보낸 뒤 1초가 지나야 정해지므로, 5초 구간 끝 1초 동안 보낸 줄은 다음 구간에서 셉니다.
- `가는길 / 오는길`: 응답에 실린 '로봇이 받은 줄 수'로 나눈 값입니다. 응답이 하나도 안 오는 동안에는 나눌 수 없어서,
  다시 응답이 온 순간 그동안의 몫이 한꺼번에 들어갑니다.
- 누적 줄 끝의 `불합격 구간 n/m` = 지금까지 5초 구간 m개 중 불합격이 n개. `첫 응답: 부팅 뒤 x초` 는 지우지 않고 계속 보여 줍니다.

### 3.2 로봇 쪽 요약 (5초마다 두 줄)

```
[로봇 5초 #12 단계2 합격] 받음 250줄(초당 50.0, 기대 50) 빠진번호 0(0.00%) | 가장 긴 공백 38 ms, 300 ms 넘는 공백 0번 | 묵은 줄 0 | 늦게 도착(가장 빠른 줄 대비) 95% 9 ms 최대 17 ms | 체크섬틀림 0 형식틀림 0 순서뒤바뀜 0 중복 0 줄밖글자 0 응답건너뜀 0 조종기재시작 0
[로봇 누적 1분00초 단계2 합격] 받음 2999줄(초당 50.0, 기대 50) 빠진번호 1(0.03%) | ... | 불합격 구간 0/12 | 첫 줄: 부팅 뒤 1.8초
```

- 로봇 쪽 숫자는 **응답이 돌아가는 길과 상관없이** 맞습니다. 조종기 쪽이 이상하면 로봇 쪽부터 봅니다.
- `줄밖글자`: 줄 시작 글자(`T`) 앞에 온 글자 수. 로봇이 켜질 때 줄 중간부터 받으면 몇 글자 생기는 것은 정상입니다.
  계속 늘면 모듈이 다른 글자를 내보내는 것이니 `[참고]` 줄에 나오는 글자를 봅니다.
- `조종기재시작`: 줄 번호·시각이 처음부터 다시 시작한 횟수(조종기 보드를 껐다 켬).

### 3.3 그때그때 나오는 알림

| 알림 | 뜻 |
|---|---|
| `[알림] 첫 응답 받음: 부팅 뒤 2.1초` / `[알림] 첫 줄 받음: 부팅 뒤 1.8초` | 링크가 처음 이어졌다. 껐다 켠 뒤 다시 이어지는 데 걸린 시간 |
| `[경고] 응답 끊김` / `[경고] 조종기 줄 끊김` | 0.3초 넘게 제대로 된 줄이 없다 → 실제 경기라면 팔이 멈춘 순간 |
| `[복구] ... 다시 옴: 1.5초 끊겼음 (그동안 빠진 번호 75개)` | 끊김이 끝났다. 끊긴 시간과 그동안 잃은 줄 수 |
| `[경고] 묵은 줄 n개: 평소보다 최대 x ms 늦게 도착` | 끊긴 동안 쌓였던 줄이 나중에 나왔다(위험 신호. 6장) |
| `[알림] 로봇 보드가 다시 켜진 것으로 보입니다` / `조종기 보드가 다시 켜진 것으로 보입니다` | 상대 보드가 재부팅됐다 |
| `[참고] 마지막으로 버린 줄: "..."` / `줄 밖 글자: "..."` | 그 5초 동안 버린 줄이나 이상한 글자가 있었을 때만 나온다. 원인 찾기에 쓴다 |
| `[참고] 지금 끊겨 있음: 3.0초째` | 요약을 찍는 순간 끊겨 있었다 |

### 3.4 LED (시리얼 모니터 없이 볼 때)

| LED | 조종기 보드 | 로봇 보드 |
|---|---|---|
| 켜짐 | 응답을 제때 받는 중 | 조종기 줄을 받는 중 |
| 빠른 깜빡임(1초에 5번) | 응답이 0.3초 넘게 끊김 | 조종기 줄이 0.3초 넘게 끊김 |
| 1초에 한 번 짧게 | 부팅 뒤 아직 응답을 한 번도 못 받음 | 부팅 뒤 아직 한 줄도 못 받음 |

BT-210 자체의 파란 LED는 켜질 때 깜빡이다가 짝이 이어지면 계속 켜져 있습니다(8장 출처 [1]).

### 3.5 명령과 기록

- 시리얼 모니터 입력칸에 `2` 를 보내면 "단계 2 시작": 누적을 지우고 요약 줄에 `단계2` 가 붙습니다. `r` 은 누적만 지웁니다.
  **단계를 시작할 때 두 보드 모두에 같은 숫자를 보냅니다.**
- 시리얼 모니터를 닫아도 시험은 계속되고 누적도 계속 쌓입니다. 다시 열면 안내문이 나오고, 다음 5초 요약의 누적 줄에 그동안의 결과가 다 들어 있습니다.
- 엑셀로 남기려면 두 스케치의 `PRINT_CSV = true` 로 올립니다. 5초마다 `CSV,...` 줄이 더 나오고, 안내문에 제목 줄이 나옵니다.
  시리얼 모니터 내용을 복사해서 `CSV,` 로 시작하는 줄만 엑셀에 붙여 넣습니다.

## 4. 합격 기준 (우리 팀이 정한 목표값 — 공식 규격이 아님)

아래 값은 BT-210이나 대회 규정이 정한 것이 아니라, **우리 로봇 펌웨어의 동작에 맞춰 정한 목표값**입니다.
스케치 맨 위 조정값으로 바꿀 수 있습니다.

| 항목 | 목표 | 왜 이 값인가 | 조정값 |
|---|---|---|---|
| 손실 (조종기) / 빠진번호 (로봇) | **1 % 미만** | 1 %면 1초에 0.5줄. 한 줄씩 띄엄띄엄 빠지는 것은 다음 줄이 20 ms 뒤에 오므로 팔에 거의 영향이 없다(추정). 그보다 많으면 링크가 불안정하다는 신호 | `LOSS_LIMIT_X100 = 100` |
| 왕복 시간 95 % 값 (조종기) | **60 ms 미만** | 한쪽 지연이 대략 30 ms 안쪽이라는 뜻(추정). 사람이 리더 팔을 움직였을 때 로봇이 늦게 따라온다고 느끼지 않을 정도로 잡았다 | `RTT_P95_LIMIT_MS = 60` |
| 0.3초 넘는 무응답(조종기) / 공백(로봇) | **한 번도 없음** | 로봇 펌웨어는 줄이 0.3초 끊기면 팔을 멈춘다(`LEADER_TIMEOUT_MS = 300`, 8장 출처 [3]). 경기 중 팔이 멈추는 일이 없어야 한다 | `SILENCE_LIMIT_MS = 300` |
| 묵은 줄 (로봇) | **0개** | 0.3초 넘게 묵은 명령을 받으면 로봇이 지난 자세로 움직인다 | `STALE_LIMIT_MS = 300` |
| BT건너뜀 / 응답건너뜀 | **0** | 0이 아니면 링크가 아니라 설정(속도·주기·길이) 문제다 | — |

- **판정 세 가지**: `불합격` = 위 기준 가운데 하나라도 어김. `주의` = 기준은 지켰지만 늦게옴·순서뒤바뀜·중복·모르는번호(조종기),
  체크섬틀림·형식틀림·순서뒤바뀜·중복·응답건너뜀(로봇)이 있었다. `합격` = 둘 다 아님.
- **한 단계의 합격**(제안): 그 단계의 **누적 줄이 두 보드 모두 `합격` 또는 `주의`** 이고, `불합격 구간 0/m`.
  `주의`가 자주 나오면 6장으로 원인을 찾습니다.
- **왕복 60 ms 기준에 대해**: 이 값은 모듈 자체의 지연을 모르는 상태에서 정한 것입니다. 1단계(가까이)에서 이미 95 % 값이 60 ms를 넘으면
  그것은 거리·전파 문제가 아니라 모듈과 설정 자체의 지연입니다. 그때는 **1단계 값 + 30 ms**를 나머지 단계의 기준으로 삼고,
  1단계 값을 팀에 공유합니다. (왕복 시간에는 보드와 모듈 사이 선로 전송 시간이 원래 들어 있습니다. 25바이트 + 28바이트를 57600 bps로 한 번 보내는 시간이 약 9 ms이고,
  줄마다 '보내는 보드 → 모듈'과 '모듈 → 받는 보드' 두 번 선로를 지나므로, 모듈이 줄을 다 받은 뒤에 무선으로 넘기면 약 18 ms가 됩니다. 실제로 어느 쪽인지는 모릅니다(추정))

## 5. 시험 순서

**준비물**: 노트북 2대(조종기용, 로봇용. 1대뿐이면 조종기 쪽만 계속 보고, 로봇 쪽은 단계 시작과 끝에만 연결해 누적 줄을 본다),
줄자, 기록표(아래), 무선조종 송신기, 경기 때 쓰는 배터리.

**공통 방법**

1. 두 보드에 시험 스케치를 올리고(2장), 경기 때와 같은 자리·같은 전원으로 둔다. 조종기는 **경기 때 잡는 자세 그대로** 든다.
2. 단계를 시작할 때 두 시리얼 모니터에 단계 번호(예: `1`)를 보낸다.
   로봇 쪽 노트북을 떼어 내야 하면, 번호를 보낸 뒤 USB를 뽑는다(배터리로 켜져 있으면 보드는 계속 돈다. 뽑을 때 재부팅되지 않는지 처음에 한 번 확인).
3. 정한 시간 동안 둔다. 단계가 끝나면 두 쪽의 **마지막 누적 줄**을 기록표에 옮긴다(로봇 쪽은 USB를 다시 꽂고 모니터를 연 뒤 다음 5초 요약을 기다린다).

| 단계 | 하는 것 | 시간 | 특히 볼 것 |
|---|---|---|---|
| **1. 가까이** | 조종기와 로봇을 1 m 거리에, 서로 보이게 둔다. 무선조종 송신기는 끈다 | 2분 | 기준값: 왕복 중간·95 %, 늦게 도착 95 %. 여기서 이미 불합격이면 거리 문제가 아니다(6장 첫 줄) |
| **2. 먼 모서리** | 조종 구역에서 조종기를 들고 서고, 로봇을 경기장(4.8 m × 4.8 m)의 **가장 먼 모서리**에 둔다. 실제 거리를 줄자로 재서 적는다(조종 구역 위치에 따라 약 6~8 m로 추정). 30초마다 로봇을 제자리에서 90°씩 돌린다 | 3분 | 손실, 가장 긴 무응답/공백, 로봇 방향에 따라 나빠지는지 |
| **3. 몸으로 가리기** | 2단계 자리에서 조종자가 로봇 쪽으로 등을 돌려, 몸이 조종기와 로봇 사이를 가리게 한다. 조종기를 가슴에 붙여 든다. 다른 사람이 로봇과 조종 구역 사이를 지나다닌다 | 2분 | 0.3초 넘는 끊김, 묵은 줄 |
| **4. 무선조종 송신기 켜고** | 2단계 자리에서 무선조종 송신기와 로봇의 수신기를 켜고(바인딩된 상태), 송신기를 경기 때처럼 조종기 바로 옆에 든다. 할 수 있으면 다른 2.4 GHz 기기(다른 팀의 무선조종·BT-210, 휴대폰 핫스팟으로 동영상 재생)를 근처에서 함께 켠다 | 3분 | 1·2단계보다 나빠지는지. 나빠지면 송신기와 BT-210 사이를 떼어 본다(6장) |
| **5. 오래 켜 두기** | 2~4단계 조건을 모두 켠 채로 둔다(조종자 움직임 포함) | 경기 시간 이상(10분 권장) | `불합격 구간 0/m`, 가끔 생기는 긴 끊김 |
| **6. 모터를 돌리면서** | 시험 스케치는 모터를 못 돌린다. **팀 코드의 BTLOG 로그 빌드 두 개**(`teleoperation_log/Leader_Grip_Track_Log`, `Follower_Grip_Track_Log`)를 올리고 2단계 자리에서 무선조종으로 바퀴를 돌리고 리더 팔로 팔을 크게 움직인다. `tools/bt_log.py` 로 기록한다(`../README.md` 2장) | 3분 | 로봇 `#R … S` 줄의 `good` 이 초당 약 30~40으로 유지되는지, `bad` 가 늘지 않는지, `GAP`·`HOLD` 줄이 한 번도 없는지 |
| **7. 전원 껐다 켜기 (로봇)** | 시험 스케치로 돌아와서, 로봇 전원(배터리와 USB 모두)을 끄고 5초 뒤 켠다. **5번** 되풀이 | 각 30초 | 로봇 쪽 `첫 줄: 부팅 뒤 x초`(로봇 모니터를 다시 연 뒤 누적 줄), 조종기 쪽 `[복구] ... x초 끊겼음`, 그 직후 묵은 줄·늦게옴 |
| **8. 전원 껐다 켜기 (조종기)** | 조종기 USB를 뽑았다가 5초 뒤 꽂는다. 5번 | 각 30초 | 조종기 쪽 `첫 응답: 부팅 뒤 x초`(모니터를 다시 연 뒤 안내문과 누적 줄), 로봇 쪽 `[복구]` 와 `조종기재시작`, 묵은 줄 |
| **9. 리셋 단추만** | 7·8단계를 전원 대신 보드의 리셋 단추로 한다(BT-210은 켜진 채 보드만 재시작) | 각 3번 | 7·8단계보다 훨씬 빨리 이어져야 한다(블루투스 연결은 그대로이므로. 추정) |

- 7·8단계의 목표(제안): **5번 모두 저절로 다시 이어질 것**(필수), 걸린 시간을 기록해 팀에 공유(참고 목표 5초 이내).
  경기 중 한쪽 보드가 재부팅되면 팔이 그 시간만큼 멈춘다는 뜻입니다.

## 6. 결과가 나쁠 때 원인 찾기

"추정"이라고 적은 것은 이 도구의 숫자로 짐작한 원인이고, 확인된 사실이 아닙니다.

| 증상 | 짐작되는 원인 | 해 볼 것 |
|---|---|---|
| 두 쪽 다 줄이 하나도 없다 (LED 1초에 한 번 짧게) | 짝이 안 이어짐, 모듈 전원·커넥터, 속도 설정 | BT-210 파란 LED가 계속 켜져 있는지(깜빡이면 짝이 안 이어진 것, 출처 [1]). 마스터·슬레이브가 맞는 보드에 있는지. 커넥터 방향. 두 스케치의 `BT_BAUD` 가 같은지(기본 57600) |
| 로봇은 잘 받는데 조종기에 응답이 없다 | 오는 길 문제: 로봇 쪽 `ECHO_ENABLED = false`, 조종기 보드 쪽 수신 선 | 로봇 안내문의 `응답 보냄`, 로봇 `응답건너뜀`. 조종기 쪽 `[참고] 줄 밖 글자` |
| 1단계(가까이)부터 왕복 95 %가 60 ms를 넘는다 | 모듈·설정 자체의 지연(추정) | 4장의 '1단계 값 + 30 ms' 규칙. 보드 쪽 문제가 아닌지 `BT건너뜀 0`, 로봇 `늦게 도착` 확인 |
| 먼 모서리·몸으로 가리기에서만 끊김이 생긴다 | 거리·가림·안테나 방향(추정) | BT-210을 보드 위쪽·바깥쪽으로, 금속 틀·배터리·모터에서 떨어지게, 조종기에서는 손과 몸에 덮이지 않게 옮긴다. 로봇 방향에 따라 다르면 모듈 방향을 바꿔 본다 |
| 무선조종 송신기를 켜면 나빠진다 | 같은 2.4 GHz 대역을 함께 쓴다(추정) | 송신기와 조종기의 BT-210을 30 cm 넘게 떼어 본다(예: 리더 팔의 BT-210 위치를 옮김). 수신기 안테나와 로봇 BT-210도 떼어 본다 |
| 체크섬틀림·형식틀림이 끊김 없이 띄엄띄엄 생긴다 | 블루투스 무선 구간에는 자체 오류 검사가 있으므로, 보드와 모듈 사이 선로(커넥터 접촉, 잡음) 쪽일 가능성(추정) | 커넥터를 다시 꽂고, 선을 모터 전선에서 떼어 놓는다. `[참고] 마지막으로 버린 줄` 의 모양을 본다 |
| 형식틀림이 `[복구]` 알림 때만 1~2개 | 끊길 때 잘린 줄. 정상 | — |
| 끊긴 뒤 `묵은 줄`·`늦게옴` 이 생긴다 | 끊긴 동안 모듈이 데이터를 쌓아 두었다가 이어진 뒤 내보낸다(추정) | 실제 로봇 펌웨어가 묵은 명령을 따라가지 않도록 하는 방법(예: 줄에 번호·시각을 넣어 오래된 줄을 버림)을 팀에서 검토. 그 전까지는 끊김 뒤 팔이 갑자기 움직일 수 있음을 조종자가 알고 있어야 한다 |
| `가는길` 은 0인데 `오는길` 만 크다 | 로봇 → 조종기 방향만 나쁘다. 실제 경기에는 영향이 적다 | 로봇 쪽 숫자(빠진번호, 공백)가 합격이면 실제 경기에는 괜찮다. 로봇 `응답건너뜀` 확인 |
| `BT건너뜀` / `응답건너뜀` 이 0이 아니다 | 보내는 양이 블루투스 속도에 비해 많다 | `BT_BAUD`, `FRAME_PERIOD_MS`, `LINE_BYTES` 를 기본값으로 되돌린다 |
| 6단계(모터)에서만 `리더 끊김`·`버림` 이 생긴다 | 모터 전류 때문에 전원이 흔들리거나 잡음이 들어온다(추정). 또는 실제 로봇 펌웨어가 바쁜 동안 블루투스 글자를 늦게 읽는다(추정) | 배터리 상태, 전원선 굵기·접촉. 시험 스케치 결과(7단계까지)와 비교해 실제 펌웨어 쪽만 나쁘면 펌웨어 쪽을 본다 |

## 9. 알아 둘 점 (한계)

- **실제 보드에서 돌려 보지 못한 상태로 전달됩니다.** 확인한 것: 두 스케치 모두 arduino-cli(보드 `OpenRB-150:samd:OpenRB-150`, 패키지 0.2.1)로
  `-Wall -Wextra` 컴파일 경고 0개. 그리고 두 스케치의 계산을 파이썬으로 옮긴 모의시험에서 가는 길 손실, 오는 길 손실, 글자 깨짐,
  끊김(버림/쌓임), 조종기·로봇 재부팅, 부팅 직후 묵은 줄, 응답 끔, 느린 링크 11가지 경우의 숫자가 실제 넣은 값과 맞는 것을 확인했습니다.
  모의시험의 '전파'는 지어낸 모형이므로, BT-210이 실제로 어떻게 동작하는지는 이 시험을 해 봐야 압니다.
- 응답을 돌려보내므로 블루투스가 실제 경기보다 조금 더 바쁩니다. 결과가 경계선에 있으면 `ECHO_ENABLED = false` 로 로봇 쪽만 다시 재 봅니다.
- 왕복 시간에는 보드 ↔ 모듈 선로 전송 시간(약 9~18 ms, 모듈이 글자를 모아 보내는 방식에 따라 다름. 4장)이 들어 있습니다. 한쪽 지연의 절대값은 잴 수 없습니다(두 보드 시계가 따로 논다).
- 손실은 보낸 뒤 1초가 지나야 정해지므로, 5초 구간의 손실은 최대 1초 늦게 반영됩니다. 누적에는 빠짐없이 들어갑니다.
- 체크섬은 실제 조종기와 같은 XOR 한 바이트입니다. 한 글자 바뀜은 모두 잡지만, 합쳐서 0이 되는 글자들이 통째로 바뀌면 못 잡습니다.
- 시험 줄과 실제 펌웨어 줄은 서로 다르므로 **한쪽만 시험 스케치를 올리면 아무것도 동작하지 않습니다**(정상). 두 보드를 같이 바꿉니다.
- 로봇 쪽 스케치는 다이나믹셀 전원을 켜지 않습니다. 팔이 처지므로 받쳐 두고, 시험이 끝나면 원래 펌웨어로 되돌립니다.
