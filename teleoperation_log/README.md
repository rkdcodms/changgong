# 블루투스 끊김 진단용 로그 빌드 (BTLOG)

`teleoperation /Leader_Grip_Track.ino`, `teleoperation /Follower_Grip_Track.ino` (main `e7ff2d7`)에 **기록 기능만 더한** 복사본과 시험 도구입니다. 팔·바퀴를 움직이는 동작은 원래 코드와 같습니다. 리더가 로봇으로 보내는 형식(`p1,p2,p3,p4,gripper_delta`)도 그대로이고, 더한 줄에는 모두 `BTLOG` 주석이 붙어 있습니다.

| 폴더 | 무엇 | 올릴 보드 |
|---|---|---|
| `Leader_Grip_Track_Log/` | 리더 로그 빌드 | 리더(손에 드는 팔) OpenRB-150 |
| `Follower_Grip_Track_Log/` | 로봇 로그 빌드 | 로봇(팔로워) OpenRB-150 |
| `tools/bt_log.py` | PC에서 로그를 파일로 저장하고 원인을 요약, GitHub `bt-logs` 브랜치에 올리기(5장) | — |
| `J12_Loopback_Test/` | OpenRB의 J12(블루투스 단자) 핀이 상했는지 보는 시험 | 의심 가는 보드 |
| `BT210_LinkTest/` | 블루투스 왕복 지연·방향별 손실을 정밀하게 재는 시험 | 두 보드 |

원래 코드와 다른 점은 네 가지입니다.

1. 두 보드가 USB로 `#L ...`(리더), `#R ...`(로봇)으로 시작하는 기록 줄을 냅니다.
2. 로봇은 1초에 한 번 요약 줄(S)을 내고, 사건이 생기면 사건 줄(GAP·HOLD·READY·LATCHED 등)도 냅니다. 이 줄들은 **블루투스로 리더에게도 보냅니다**. 리더 로그 빌드가 받아서 USB로 넘겨 주므로, **리더에 노트북 한 대만 꽂아도 양쪽 기록이 남습니다.**
   - 무선이 끊긴 동안의 로봇 줄은 리더에 도착하지 않습니다. 끊김 정보는 연결이 돌아온 뒤 GAP 줄로 옵니다.
   - 끊긴 동안의 로봇 기록까지 보려면 로봇도 USB로 노트북에 꽂으세요.
   - 원래 리더 코드는 블루투스로 들어오는 글자를 읽지 않습니다. 그래서 로봇에만 로그 빌드를 올려도 문제없습니다.
3. 리더가 보내는 프레임을 USB로 그대로 찍던 출력은 껐습니다(`ECHO_FRAMES_TO_USB = false`). 그대로 두면 로그가 너무 길어집니다.
4. 기록은 제어 동작 밖에서, 기다리지 않고 씁니다. 원래 코드의 `if (Serial)` 검사는 부를 때마다 10 ms를 멈추는데(OpenRB 코어 동작), 기록 쪽은 이 검사를 쓰지 않습니다.

## 0. 먼저: BT-210 전원은 3.3 V입니다

**사양**
- ROBOTIS 공식 사양:
  - BT-210 **동작 전압은 3.3 V**이고, VCC 핀은 "3.3 V DC 입력"입니다.
  - 신호(UART)도 3.3 V 레벨입니다.
  - 컨트롤러 전원이 꺼진 상태에서만 연결하라는 주의가 있습니다.
  - 출처: [BT-210 e-Manual](https://emanual.robotis.com/docs/en/parts/communication/bt-210/). 수업 자료 Arduino Workshop 4의 7쪽 표에도 같은 내용이 있습니다.
- OpenRB-150 신호 핀이 견디는 최대 전압은 3.3 V입니다. 출처: [OpenRB-150 e-Manual](https://emanual.robotis.com/docs/en/parts/controller/openrb-150/)

**5 V에 연결했을 때 생길 수 있는 일** (사양에서 추론한 것이고 실제로 확인하지는 않았습니다)
- 모듈이 사양보다 높은 전압으로 동작해 불안정해지거나 리셋되고, 무선 연결이 끊겼다가 다시 붙습니다. 이때 파란 LED가 다시 깜빡입니다.
- 모듈 내부가 5 V로 동작하면, 모듈이 내보내는 신호가 OpenRB의 J12 수신 핀(Rx) 한계인 3.3 V를 넘을 수 있습니다. 그러면 **OpenRB 쪽 수신 핀이 상할 수도 있습니다.**
- 반대로 OpenRB가 보내는 3.3 V 신호를 모듈이 '1'로 못 읽어서 글자가 깨질 수 있습니다.
- 오래 5 V로 쓴 모듈은 고장 났을 수 있습니다. 그러면 배선을 고친 뒤에도 계속 끊길 수 있습니다.

**어떻게 연결했는지 먼저 확인하세요**
- 수업 방법(Workshop 4, 14쪽): OpenRB의 4핀 자리 **J12(`Tx Rx V G`)**에 커넥터를 납땜하고, BT-210 케이블을 그대로 꽂습니다.
  - 이 경우 전압을 사람이 고르지 않았습니다.
  - J12의 V 핀 전압은 OpenRB 문서에 글로 적혀 있지 않습니다. 같은 BT-210용 4핀 단자를 가진 형제 보드 OpenCM9.04는 3.3 V로 명시하고 있어서, J12 V도 3.3 V일 가능성이 큽니다.
  - 회로도: robotis.com/service/download.php?no=2117
- 점퍼선으로 OpenRB 핀 헤더의 `+5V` 핀에 연결했다면, 그것이 정격을 벗어난 배선입니다.

**고치는 법**
1. **배터리와 USB 케이블을 모두 뽑습니다.** USB만 꽂혀 있어도 보드에는 전원이 들어와 있습니다.
2. BT-210을 빼고 보드 전원을 켭니다. 모듈을 꽂을 자리의 **V–G 전압을 멀티미터로 재서 3.3 V 근처인지** 확인합니다.
   - J12를 쓴다면 J12의 V–G를 잽니다.
   - 헤더를 쓴다면 `+3V3`–`GND`를 잽니다.
3. 다시 전원을 모두 끄고 연결합니다.
   - **전원**: J12의 V, 또는 헤더의 `+3V3` 핀.
     - 헤더의 `+3V3`은 `VIN`(배터리 전압, 최대 12.6 V) 바로 옆에 있습니다. 한 칸만 밀려도 모듈이 탑니다.
     - J12 바로 아래 JP1 점퍼(`VIN(DXL)` / `+5V`) 핀에서는 절대 전원을 따지 마세요.
   - **신호**: 반드시 **J12의 Tx/Rx**에 연결합니다.
     - 이 코드는 `Serial2`만 쓰고, `Serial2`는 J12에만 나와 있습니다.
     - 헤더에 `TX`/`RX`라고 적힌 D14/D13 핀은 `Serial3`이라서 동작하지 않습니다.
     - 선은 엇갈리게 연결합니다: OpenRB `Tx` → BT-210 `RXD`(1번), OpenRB `Rx` → BT-210 `TXD`(2번), `G` → `GND`(4번), `V` → `VCC`(3번).
     - ROBOTIS 케이블을 방향만 맞게 J12에 꽂으면 저절로 이렇게 됩니다.
4. 전원을 켜고 BT-210의 VCC–GND가 3.3 V 근처인지 다시 잽니다. 신호선 두 개도 아무것도 안 보낼 때 3.3 V 이하여야 합니다.
5. 5 V로 썼던 보드는 `J12_Loopback_Test`로 J12 핀이 멀쩡한지 확인합니다. BT-210을 빼고 J12의 Tx와 Rx를 선 하나로 잇습니다. `PASS`가 나오면 핀은 괜찮은 것입니다.
6. 리더와 로봇 **양쪽 모두** 확인합니다. 고친 뒤에도 끊기면 BT-210 한 쌍을 바꿔 봅니다. 고치기 전과 후를 이 로그 빌드로 기록해 비교합니다.

## 1. 올리기

1. Arduino IDE에서 보드를 **OpenRB-150**으로 고릅니다. 필요한 라이브러리는 원래 코드와 같은 Dynamixel2Arduino입니다.
2. `Leader_Grip_Track_Log/Leader_Grip_Track_Log.ino` → 리더 보드에 업로드합니다.
3. `Follower_Grip_Track_Log/Follower_Grip_Track_Log.ino` → 로봇 보드에 업로드합니다.
4. 시리얼 모니터에서 로그 빌드인지 확인합니다.
   - 리더: 1초마다 나오는 `[LEADER] sent=… build=LEADER_GRIP_TRACK_20261112_BTLOG …` 줄과 `#L … S` 줄이 보이면 됩니다.
   - 로봇: `#R … S` 줄(1초마다)이 보이면 됩니다.
   - 첫 줄의 `[BUILD]`는 켜진 직후 0.5초 안에 찍혀서 보통 보이지 않습니다.

원래대로 돌리려면 `teleoperation /`의 원래 파일을 다시 올리면 됩니다.

## 2. 기록하기

### 방법 A: 파이썬 도구 (추천)

`teleoperation_log\tools` 폴더에서 명령 창을 엽니다(탐색기 주소창에 `cmd` 입력). 그다음 순서대로 실행합니다.

```bash
python -m pip install pyserial
```

```bash
python bt_log.py --list
```

```bash
python bt_log.py COM5
```

- `COM5` 자리에 리더 보드 포트를 넣습니다. 로봇 보드도 USB로 꽂았다면 `python bt_log.py COM5 COM7`처럼 둘 다 적습니다.
- 끊김이 몇 번 일어날 때까지 평소처럼 조종하고 **Ctrl+C**로 멈춥니다.
- `tools\logs\`에 두 파일이 생깁니다.
  - `bt_날짜_시각.log`: 전체 기록
  - `..._요약.txt`: 원인 요약
- 저장해 둔 로그를 다시 요약하려면 아래처럼 실행합니다.

```bash
python bt_log.py --analyze logs\bt_20261113_150102.log
```

### 방법 B: 아두이노 IDE 시리얼 모니터

1. 리더 보드 포트로 시리얼 모니터를 열고 시각 표시(타임스탬프)를 켭니다.
2. 끊김이 일어난 뒤 창의 글을 전부 복사해 `.txt`로 저장합니다.
3. `python bt_log.py --analyze 저장한파일.txt`로 요약합니다. 이때는 pyserial이 없어도 됩니다.

## 3. 시험 순서 (한 번에 2~3분씩)

| 순서 | 상황 | 볼 것 |
|---|---|---|
| 1 | 책상 위, 리더와 로봇 1 m 거리, 모터 전원 켜고 가만히 | 기준값. 여기서도 끊기면 배선·전원 문제 |
| 2 | 같은 자리에서 팔을 크게, 빠르게 움직이기 | 모터 전류가 클 때 끊기는지(전압 강하·재부팅) |
| 3 | 주행 + 방지턱·경사로 | 충격·진동에 끊기는지(접촉 불량, 모듈 고정) |
| 4 | 경기장 먼 구석(약 5~7 m), 몸으로 가리기 | 거리·가림 |
| 5 | 다른 팀 조종기(2.4 GHz)가 켜진 곳 | 간섭 |

**끊길 때마다 BT-210의 파란 LED를 보고 메모하세요.**
- 깜빡이면: 무선 연결이 끊겼다가 다시 연결하는 중입니다.
- 계속 켜져 있으면: 무선은 붙어 있는데 데이터가 안 오는 것입니다.
- 이 차이는 보드가 알 수 없어서 로그에 남지 않습니다.

## 4. 로그 읽는 법

모든 기록 줄은 `#R <로봇 보드 ms> <종류> 키=값 ...` 또는 `#L <리더 보드 ms> <종류> ...` 형식입니다.

| 줄 | 뜻 |
|---|---|
| `#R ... S` (1초마다) | 로봇의 1초 요약. 각 값의 뜻은 표 아래 목록에 있음 |
| `#R ... GAP` | 정상 줄이 150 ms 이상 안 온 구간이 **끝났을 때** 한 줄. `cls`가 원인 종류(아래 표), `sil`은 그동안 글자가 하나도 안 온 가장 긴 시간(ms) |
| `#R ... GAP_OPEN` | 아직 끝나지 않은 끊김. 1초 이상 이어지는 동안 1초마다 나옴 |
| `#R ... HOLD` | 원래 코드의 0.5초 시간초과가 걸려 팔이 그 자세로 멈춤 |
| `#R ... READY` / `BOOT` | 로봇 셋업이 끝남 / 켜진 뒤 첫 보고. `rst`는 켜진 이유 |
| `#R ... LATCHED` | 로봇이 고장 래치 상태. 블루투스와 무관하게 팔이 안 따라오며, 전원을 다시 넣어야 풀림 |
| `#L ... S` (1초마다) | 리더의 1초 요약. 각 값의 뜻은 표 아래 목록에 있음 |
| `#L ... SENDGAP` | **리더 자신이** 150 ms 이상 안 보냄. `why`가 이유 |
| `#L ... ROBOT_SILENT` / `ROBOT_BACK` | 로봇 기록이 2.5초 넘게 안 돌아옴 / 다시 옴. `bytes_meanwhile`이 0이면 아무것도 안 온 것, 0보다 크면 글자는 왔는데 깨진 것 |
| `#L ... FROM_ROBOT #R ...` | 블루투스로 돌아온 로봇 기록 줄 |
| `#L ... BOOT` / `LATCHED` | 리더가 켜짐 / 리더가 래치되어 보내기를 영구히 멈춤 |

로봇 S 줄의 값:
- `good`: 정상 줄 수(초당 약 30~40)
- `bad`: 버린 줄 수. `why=c깨진글자/l너무긴줄/p형식오류`로 이유를 나눕니다
- `gapmax`: 가장 긴 공백(ms)
- `since_good`: 마지막 정상 줄 이후 지난 시간
- `loopmax_us`: 가장 느린 loop. 원래 코드도 loop 한 번에 10 ms 이상 걸립니다
- `rxpeak`: 수신 버퍼 최대(256이면 넘침)
- `vin`: 모터 전원 전압 범위
- `link`, `fault`: 연결 상태와 고장 상태
- `rst`: 켜진 이유

리더 S 줄의 값:
- `sent`: 보낸 줄
- `rej`: 리더 모터 읽기 실패로 못 보낸 줄
- `busy`: 송신 버퍼가 차서 건너뛴 줄
- `sendgap`: 가장 긴 보내기 공백
- `robot_lines` / `robot_bad` / `robot_bytes`: 로봇에서 받은 정상 줄, 깨진 줄, 바이트 수
- `robot_age`: 로봇 기록이 마지막으로 온 뒤 지난 시간
- `state`: 리더 상태

### GAP의 `cls`로 원인 가르기

| cls | 뜻 | 다음에 볼 것 |
|---|---|---|
| `NO_DATA` | 끊긴 시간 대부분 동안 글자가 하나도 안 왔다 | 같은 시각에 리더 `SENDGAP`이 있으면 **리더가 안 보낸 것**(리더 모터 읽기 실패 등). 없으면 **무선 연결 끊김**: BT-210 LED, 3.3 V 전원, 거리·가림·간섭 |
| `BAD_DATA` | 글자는 계속 왔는데 깨져서 버렸다 | **배선·전압(5 V!)**, 커넥터 방향, 납땜, 보드레이트 |
| `PARTIAL` | 몇 글자만 오고 줄이 완성되지 않았다 | NO_DATA와 같이 봄 |
| `SLOW_LOOP` | 로봇 보드가 바빠서 못 읽었다 | `loopmax_us`가 크면 다이나믹셀 응답 시간초과가 겹친 것 |

**로봇 ms가 처음부터 다시 시작하거나 READY 줄이 다시 나오면 로봇 보드가 재부팅된 것입니다.**
- `rst`가 `POWER_ON`이든 `BROWNOUT_3V3`이든, 사람이 껐다 켠 것이 아니면 전원 문제입니다(배터리·커넥터·전원선).
- `RESET_PIN`은 리셋 버튼, `SOFTWARE`는 업로드입니다.
- 이 보드는 브라운아웃 감지 설정이 확인되지 않았습니다. 그래서 전압이 크게 떨어져도 `POWER_ON`으로 나올 수 있습니다.

`bt_log.py` 요약은 이 판단을 자동으로 해 주지만, 로그만으로 5 V가 원인이었다고 **증명할 수는 없습니다**. 측정(0장)과 고치기 전·후 비교로 확인하세요.


- 저장소에 **쓰기 권한(collaborator)**이 있는 GitHub 계정이 필요합니다. 처음 올릴 때 GitHub 로그인 창이 뜨면 로그인합니다(Git for Windows의 Git Credential Manager).
- git 이름과 이메일을 설정하지 않았다면 커밋 작성자가 `bt_log uploader`로 표시됩니다. 자기 이름으로 남기려면 아래 명령을 한 번 실행합니다. 이메일은 GitHub에 공개되므로, 개인 메일 대신 GitHub의 noreply 주소(GitHub 설정 → Emails)를 쓰는 것을 권합니다.

```bash
git config --global user.name "이름"
```

**기록하면서 끝날 때 바로 올리기**

```bash
python bt_log.py COM5 --upload --note "주행+방지턱, 끊길 때 LED 깜빡임, BT-210 3.3V로 고친 뒤"
```

**이미 저장된 로그 올리기** (요약 파일이 없으면 만들어서 같이 올림)

```bash
python bt_log.py --upload-file logs\bt_20261113_150102.log --note "책상 위 1m, 5V 연결 상태"
```

- `--note`의 메모는 커밋 메시지에 들어갑니다. 다음 내용을 적어 주세요.
  - 끊길 때 BT-210 LED가 깜빡였는지
  - 그때 하던 동작(정지, 팔 움직임, 주행, 방지턱)
  - BT-210을 **어떻게** 연결했는지(J12 케이블인지, 점퍼선으로 어느 핀인지)와 몇 V였는지
- 올리기가 끝나면 GitHub 주소(`.../tree/bt-logs/logs/<날짜>`)가 나옵니다.
- 올리기가 실패해도 로그 파일은 `tools\logs\`에 그대로 남습니다. 인터넷이나 권한 문제를 해결한 뒤 `--upload-file`로 다시 올리면 됩니다.
- 여러 사람이 동시에 올려도 됩니다. 같은 이름의 파일이 있으면 `_2`를 붙여 올립니다.

**올라온 로그 보기**: GitHub에서 브랜치를 `bt-logs`로 바꾸거나, 아래 명령으로 받아서 봅니다.

```bash
git fetch origin bt-logs
```

```bash
git log --stat origin/bt-logs
```
